# keel/qt5compat: Qt 5 QML APIs for unported Sailfish apps

Tier B (`docs/plan.md`) means a Sailfish app rebuilds against Keel with no QML source changes. After Keel's own gaps, most corpus failures were Qt 5 QML APIs that Qt 6 removed or changed, used in the apps' own QML (cause **Q** in `corpus/results/`). These QML-only modules give those apps the Qt 5 names back, on top of Qt 6. They are installed into a Keel-specific import directory (`%{_libdir}/keel/qt5compat`, which is `/usr/lib64/keel/qt5compat` on aarch64) that keel-shell puts first on `QML_IMPORT_PATH` for the apps it runs. Nothing is installed into Qt 6's QML directory, so other Qt 6 programs never see them.

| Import the app writes | What it gets | Corpus apps |
| --- | --- | --- |
| `import QtGraphicalEffects 1.x` | Qt5Compat.GraphicalEffects, re-exported (`qmldir` `import`). Same types and API. Needs Chum's `qt6-qt5compat` on the device. | foilauth, foilnotes, hutspot, sfos-forum-viewer, yubikey, communi |
| `import QtFeedback 5.0` | `ThemeEffect`, `HapticsEffect`, `FileEffect`, `Feedback` (enums). **No-op**: no vibration; `ThemeEffect.supported` is false; `HapticsEffect` runs its state machine for `duration` ms. | counter, yubikey, foilauth, wordle |
| `import QtQuick 2.0` to `2.14` | Qt Quick as usual, plus `RegExpValidator` (on `RegularExpressionValidator`; `regExp` takes a JS RegExp or a pattern string) and `VisualItemModel` (Qt 6's `ObjectModel`); `Screen` is Silica's (Keel.SilicaScreen, a superset of Qt Quick's Screen), as in Qt 5, whose Qt Quick 2.x had no `Screen`. | nextcloudnotes, bitsailor, harbour-lib's colour editor; communi |
| `import QtMultimedia 5.x` | Qt 5 API wrappers over Qt 6 Multimedia: `MediaPlayer` and `Audio`, `VideoOutput` (`source: player` or `source: camera`), `SoundEffect`, `Camera` (with `flash`, `exposure`, `focus`, `imageProcessing`, `imageCapture`, `viewfinder`, `videoRecorder`; on Qt 6's `CaptureSession`, `Camera` and `ImageCapture`), `CameraImageProcessing` enums, the `QtMultimedia.availableCameras` singleton. Needs `qt6-qtmultimedia`. | nayttamo, hafenschau, counter; foilauth and yubikey (`Camera` in ScanPage/ViewFinder) |

The 2026-10-01 corpus run with these modules ([`corpus/results/2026-10-01-3.md`](../../corpus/results/2026-10-01-3.md)) moved tier B from 7 to 10 of 19 apps; the only Q failure left was hafenschau's `const x;` (Qt 6's JavaScript engine rejects a `const` without initializer), which no QML module can provide. Since the eighth run ([`corpus/results/2026-10-02-8.md`](../../corpus/results/2026-10-02-8.md)) Keel loads such code through a rewrite of the app's own sources (below), and hafenschau reaches tier B.

## How the QtQuick and QtMultimedia shims work

Qt cannot be given extra types in its own `QtQuick` or `QtMultimedia` URIs, and an app that writes `import QtQuick 2.0` and uses `RegExpValidator` imports nothing else that could provide it. The shims use Qt's module lookup instead: for `import QtQuick 2.6`, Qt looks for `QtQuick.2.6/qmldir`, then `QtQuick.2/qmldir`, then `QtQuick/qmldir`, in each import path. So:

- `QtQuick.2.0` to `QtQuick.2.14` (generated by `CMakeLists.txt`) each contain a `qmldir` that re-exports the real Qt Quick (`import QtQuick 2.15`, which no shim directory matches, so Qt's own module answers), `KeelQt5Compat.QtQuick` (the two Qt 5 types) and, last, `Keel.SilicaScreen` (keel/silica). Qt 6 resolves an unqualified type name to the first of a file's imports that has it, and among a qmldir's re-exports to the last, so without that line `Screen` was Qt Quick's attached Screen whenever a file imported QtQuick before Sailfish.Silica (the usual order), and Silica's `sizeCategory`, `topCutout` and size enums were undefined (found by Shoal Camera). With it, `Screen` is Silica's in either order (`tests/silicascreen`), and Keel's Screen carries Qt Quick's Screen members too, so code written for those keeps working. Checked on Qt 6.4.2 (host); not yet run on 6.8. Only imports of `QtQuick 2.15` and `6.x` bypass the shims. Keel's Silica module is mostly Silica's BSD QML, which imports `QtQuick 2.0` to `2.6`, so under keel-shell those files resolve Qt Quick through the shim directories as well. They still get Qt's own Qt Quick types (the re-export adds names, it does not copy types): `tests/core/tst_qtquick_identity.qml` checks this for every minor version, and `keel_qt5compat_silica_regression` runs Keel's Silica tests with the shims first on the import path. The generated `qmldir` deliberately has no `module QtQuick` line: with it, Qt 6.8.4 refuses to register Qt Quick's own types afterwards ("Namespace 'QtQuick' has already been used for type registration"), while Qt 6.4 accepts both forms.
- `QtMultimedia.5/qmldir` declares `module QtMultimedia` with the Qt 5 wrappers. It does not re-export Qt 6 Multimedia: every type an app gets under `import QtMultimedia 5.x` is one of the wrappers, which use Qt 6's module internally (`import QtMultimedia 6.0 as QM`). The corpus apps use only wrapped types (`MediaPlayer`, `Audio`, `VideoOutput`, `SoundEffect`, `Camera`, `CameraImageProcessing`, `QtMultimedia.availableCameras`). `import QtMultimedia 6.x`, and an unversioned `import QtMultimedia`, still go to Qt's module (`tests/camera/tst_qt6_import.qml`). The wrappers are compositions (`MediaPlayer` is a `QtObject` holding a Qt 6 `MediaPlayer` and `AudioOutput`), so Qt 5 names that clash with newer Qt 6 members (the `playing()` signal, the `error()` signal) work on both 6.4 and 6.8.
- `Camera` is a `QtObject` with the Qt 5 API (enums with Qt 5's numbering, `cameraState`/`cameraStatus`, `start()`/`stop()`/`searchAndLock()`/`unlock()`, `deviceId`, `position`, `digitalZoom`, grouped `flash`/`exposure`/`focus`/`imageProcessing`/`imageCapture`/`viewfinder`/`videoRecorder`/`metaData`). It creates a Qt 6 `CaptureSession` with a `Camera` and an `ImageCapture` only while `MediaDevices` lists a camera, and `VideoOutput { source: camera }` creates its Qt 6 `VideoOutput` only then and hands it to the session. Without a camera `availability` is `Camera.Unavailable`, `cameraStatus` `Camera.UnavailableStatus`, and `imageCapture.capture()` returns -1 with `captureFailed`. Qt 5 settings map to Qt 6 where Qt 6 has them: `flash.mode` to `flashMode`/`torchMode` (`FlashTorch` is the torch), `focus.focusMode` to `focusMode`, `FocusPointCustom`/`FocusPointCenter` to `customFocusPoint`, exposure mode and compensation, manual ISO and shutter speed, white balance mode and `manualWhiteBalance`, `digitalZoom` to `zoomFactor`, `viewfinder.resolution` to a matching `cameraFormat`, `imageCapture.capture()` to `captureToFile("")` (Qt 5 saved to the default location too).

Both were tested on Qt 6.4.2 (host) and Qt 6.8.4 (the SDK target's Qt, under qemu; see "Tests").

**Compatibility risk of the QtQuick re-export.** Re-exported types are visible regardless of the app's minor version, so an app importing `QtQuick 2.0` also sees types Qt Quick added up to 2.15 (`TableView`, `TapHandler`, `DragHandler`, `PointHandler`, ...). Property revisions are still enforced (`Item.containmentMask` stays unavailable under 2.0; tested). An app that has its own component with one of those newer names could resolve the name to Qt Quick's type instead of its own. No corpus app does (the corpus run shows no new failure). Without the shims Qt 6 already fails these apps, so the risk only affects apps the shims are meant to help.

**Alternative considered: exporting `RegExpValidator` and `VisualItemModel` from Keel's `Sailfish.Silica`** (every corpus app imports Silica). Rejected: neither is a Silica name, so Keel would add non-Silica API to its Silica module, visible to new Keel apps too, and the version-qualified directories achieve the same without touching keel/silica. If the QtQuick lookup ever stops working (a future Qt dropping version-qualified module directories), the Silica export is the fallback: one line in `keel/silica`'s `qmldir`, `import KeelQt5Compat.QtQuick 1.0`, which would re-export both types into Silica's namespace (not tried).

## Qt 5 JavaScript in app sources

Sailfish OS ran apps on Qt 5.6, whose JavaScript engine accepted code that Qt 6's rejects when it compiles the file: then the whole file (and every page that uses it) fails to load. hafenschau's models declare `const items` without an initializer and assign it in an `if`/`else`; Qt 5.6 treated `const` like `var` (ES5 engine: function scope, assignable). No module can stand in for that, so Keel rewrites the source instead, before Qt compiles it ([`src/qt5source.h`](src/qt5source.h), static library `keel-qt5compat-source`).

- **The rewrite** is done on tokens, not with a pattern over the text: a JavaScript tokenizer (identifiers, numbers, strings, template literals with code inside `${...}`, regular expression literals with classes, comments, punctuators; QML files use the same tokens) finds `const` declarations and parses their declarator lists (destructuring patterns, initializers up to the next top-level `,`, `;` or automatic semicolon). A declaration with a declarator that has no initializer (`const x;`, `const a, b = 1;`, `const items` followed by a new line) becomes `var` (padded to `var  `, so every line and column stays where it was). `for (const x of y)`, `for (const k in o)`, initialized declarations, member names (`a.const`, `{ const: 1 }`) and anything in strings, templates, regular expressions and comments stay. Only code Qt 6 cannot compile is changed, so a file that already compiles on Qt 6 comes back unchanged. `var` rather than `let`: it is what Qt 5.6 executed (function scope, no temporal dead zone), so code that reads the variable after the block that assigned it keeps working.
- **Loading**: a `QQmlAbstractUrlInterceptor` (`QQmlEngine::addUrlInterceptor`) sees every QML and JavaScript file the engine loads. For files below the app's directories only, it reads the file; if it contains `const` and the rewrite changes it, the interceptor returns the URL of a rewritten copy. Qt reads the copy but keeps the original URL as the file's logical URL (`QQmlDataBlob::finalUrl()`), so relative imports, `qmldir` lookups, `Qt.resolvedUrl()` and component type names are those of the original file. **Up to Qt 6.8 only** (the phone's Qt): from Qt 6.10 `QQmlImports` looks a type up by its intercepted URL, so a rewritten file's relative imports resolve against the copy's directory and fail (the test expects this failure on 6.10+). Supporting Qt 6.10+ needs the copies laid out as a mirror of the app tree. Compile errors in a rewritten file name the copy, at the original line and column (the log line maps it back; the corpus harness rewrites the URL). Decisions are remembered per file (modification time and size), so each file is read once per process.
- **Cache**: copies are content-addressed (a hash of the rewrite version and the original bytes as directory, the original file name kept, since Qt tells `.mjs` modules by the extension) in the first writable of `$KEEL_QT5COMPAT_CACHE`, `$XDG_CACHE_HOME/keel/qt5compat` (`~/.cache/keel/qt5compat`), the app's own cache directory + `/keel-qt5compat` (the one Sailjail lets an app write) and a directory under `/tmp`. Qt's own QML disk cache then keys on the copy. Each rewritten file is logged once per process (info, category `keel.qt5compat.source`: file, number of declarations, copy).
- **When it is on**: always, for the app's own data directory, in `SailfishApp::createView()` (keel/sailfishapp; also the booster's preloaded view), so SDK-style apps and boosted apps get it without changes; `KEEL_QT5COMPAT_SOURCE=0` turns it off. Not opt-in, because the apps that need it are exactly the unported ones nobody will add a desktop key to, and because it only ever changes code that Qt 6 refuses to compile: for an app that already runs on Qt 6 it is a no-op (one read of each app file that contains `const`). Keel's and Qt's own modules are never rewritten (they are not below the app's directory). Apps that make their own engine (the Rust apps) do not get it; they are Qt 6 code. QML in `qrc:` resources is not covered (Harbour apps install their QML under `/usr/share/<app>`).
- **Corpus harness**: `keel-load --app-root DIR` compiles in the same source file and installs it for the app's checkout (`corpus/harness/load-corpus.py` passes it for every page); the results list the files loaded rewritten per app.

Other Qt 5 JavaScript that Qt 6 rejects was not found in the corpus (2026-10-02: only hafenschau's two `const` declarations). Qt 6 still accepts, with deprecation warnings, implicit `onFoo` handlers in `Connections` and objects assigned to signal handlers; those are left alone. Not handled: assignments to an initialized `const` (`const a = 1; a = 2`) and `const` loop counters (`for (const i = 0; ...; i++)`), which Qt 5.6 allowed and Qt 6 rejects only when the assignment runs (TypeError); finding them needs scope analysis, and no corpus app does it.

## Wiring: keel-shell

keel-shell puts the directory first on the app's `QML_IMPORT_PATH`, ahead of anything inherited; see `LaunchConfig::buildEnvironment` in `keel/shell/src/core/launchconfig.cpp` and `keel/shell/PROTOCOL.md` section 1. The directory is fixed when keel-shell is built (`KEEL_QT5COMPAT_DIR`, from Qt's library directory, so it matches `%{_libdir}` on 32-bit and 64-bit targets alike). `--env QML_IMPORT_PATH=...` still overrides it, since `--env` is applied last. Apps started without keel-shell (desktop runs, `keel-load`) need the directory on `QML_IMPORT_PATH` by hand, as the tests and the corpus harness do.

- `shipwright-keel-qt5compat` (`keel/rpm/shipwright-keel-qt5compat.spec`): `Requires: qt6-qt5compat >= 6.8`, `Recommends: qt6-qtmultimedia >= 6.8`. Chum `chum:testing` 5.2 (aarch64) ships both: `qt6-qt5compat-6.8.4-1.3.1.bso` contains `/usr/lib64/qt6/qml/Qt5Compat/GraphicalEffects`, and `qt6-qtmultimedia-6.8.4+git2-1.6.1.bso` has the ffmpeg and GStreamer backends. Nothing has to be built or mirrored by Reef beyond Chum's packages. ## Limits

- **QtFeedback is a no-op.** On a device it should play through Nemo NGF (`ngfd`, D-Bus `com.nokia.NonGraphicFeedback1.Backend`, method `Play(event, properties)`), which Keel's `Nemo.DBus` could call from QML. Not done: the mapping from `ThemeEffect` values to NGF event names could not be checked here, and whether a Sailjailed app may reach `ngfd` needs a device.
- **Enum values that Qt 5 defines as -1** cannot be QML enum values on Qt 6.4: `MediaPlayer.Infinite` and `Feedback.Infinite` are `INT_MAX` here (the wrappers treat them and any negative value as infinite), and `ThemeEffect.Undefined` is 65534. Code that uses the names works; code comparing them with a literal `-1` does not.
- `MediaPlayer`: no `error` property (QML cannot have a property and a signal of the same name; `onError` works and `errorString` is there), no `playlist`, `audioRole`, `notifyInterval` or `mediaObject`; `autoLoad` is accepted and ignored (Qt 6 always loads). `VideoOutput`: `filters` is accepted and ignored with one warning (Qt 5 video filters are C++ `QAbstractVideoFilter`s, which Qt 6 does not have; a QZXing-style filter scans nothing); `autoOrientation` and `flushMode` are accepted and ignored; the `map*()` functions are computed from `contentRect`, `sourceRect` and `orientation` (`VideoGeometry.js`). Not provided at all: `Radio`, `Playlist`, `Torch`, `Video`, `QtMultimedia.convertVolume()`.
- `Camera`: `cameraState` is the requested state, as in Qt 5, so it reads `ActiveState` on a machine without a camera; `cameraStatus` is what happened. `start()` and `stop()` assign `cameraState`, which drops an app's binding on it unless the state is unchanged (Qt 5's C++ setter kept bindings). Qt 6 has no focus lock: `searchAndLock()` reports `Locked` at once when the camera is active. `focus.focusZones` is always empty (Qt 6 does not report focus areas), `orientation` is Qt 6.7+'s `cameraDevice.correctionAngle` (0 on Qt 6.4), `captureMode` is accepted (the session always has the image capture), metering, aperture, brightness/contrast/saturation/sharpening/denoising and colour filters are accepted and ignored, `metaData` is accepted but not passed to Qt 6 (no app-set EXIF orientation or GPS in photos), `mediaObject` and optical zoom are not provided, `imageCapture.imageMetadataAvailable` is never emitted, and `videoRecorder.record()` warns once and does not record. On Qt 6.4 listing cameras needs a Qt Multimedia backend (without one Qt aborts, as it does for `MediaPlayer`); on the device Chum's `qt6-qtmultimedia` has the ffmpeg and GStreamer backends. Whether those backends see a Sailfish device's cameras (droid camera HAL) is not known: on a device without a Qt 6 camera backend, apps get the no-camera behaviour above.
- `RegExpValidator`: QRegExp-only syntax (wildcard mode, minimal matching) is not translated. `VisualItemModel`: the attached `VisualItemModel.index` is not provided (`ObjectModel.index` is). `VisualDataModel` is not provided.
- Qt 6's JavaScript engine differences are handled only where Qt 6 refuses to compile (`const` without initializer, see "Qt 5 JavaScript in app sources"); runtime differences (assigning an initialized `const`) are not.
